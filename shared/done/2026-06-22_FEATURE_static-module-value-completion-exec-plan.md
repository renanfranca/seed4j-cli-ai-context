# Static Module Value Completion

This ExecPlan is a living document. Keep `Progress`, `Decisions`, `Risks`, and `Lessons Learned` up to date as work advances.

## Purpose / Big Picture

Deliver phase 1 of GitHub issue #256 in seed4j-cli. Static Bash completion generated by `seed4j completion bash` should expose known valid module option values, not only a module property's `defaultValue`, so users and agents can discover values such as `npm`, `pnpm`, `yaml`, `properties`, `lf`, and `crlf` directly from completion output. This task is limited to authorized maintenance of this repository.

## Scope

In scope: static Bash value completion, focused tests, README updates, and command documentation updates.

Out of scope: `--plan`, `--format json`, parameter source metadata, dynamic history-aware completion, parsing `.seed4j`, and changes to `/home/renanfranca/projects/seed4j`.

## Definitions

Static completion means completion generated once by `seed4j completion bash`; it does not query runtime project state.

Known module property candidates are CLI-owned candidate lists for selected Seed4J property keys.

Insertable value means the raw shell value inserted by completion, such as `pnpm`; it must not include labels such as `pnpm (from history)`.

## Existing Context

`ApplyModuleSubCommand` currently sets module option candidates from `property.defaultValue()` only. `BashCompletionScriptGenerator` serializes Picocli `completionCandidates()` into the static Bash script and already handles prefix filtering. `README.md` and `documentation/Commands.md` currently describe value completion as default-metadata based.

## Desired End State

`seed4j completion bash` generates static candidates where `--node-package-manager` has `npm` and `pnpm`, `--spring-configuration-format` has `yaml` and `properties`, and `--end-of-line` has `lf` and `crlf`. Unknown properties still fall back to their default value. Duplicate values are removed while preserving order. `--no-complete-values` still suppresses value candidates. Documentation describes known values plus default fallback and explicitly says project history is not read.

## Decisions

- Decision: Keep the known-value catalog in primary CLI infrastructure.
  Rationale: This is shell-completion presentation behavior and must not affect domain apply semantics.
  Date/Author: 2026-06-22 / Codex

- Decision: Do not modify `seed4j/seed4j` in this phase.
  Rationale: Public enums already provide enough source data for two properties, and end-of-line can be a small CLI-owned static list.
  Date/Author: 2026-06-22 / Codex

- Decision: Treat `--plan` as a separate future phase.
  Rationale: This checkout has no existing apply `--plan` contract, and introducing it would expand the behavioral surface beyond static completion.
  Date/Author: 2026-06-22 / Codex

## Risks and Mitigations

- Risk: Documentation implies completion reads project state.
  Mitigation: Explicitly state completion is static and history-free.

- Risk: The catalog grows into domain logic.
  Mitigation: Limit it to completion candidates and keep apply semantics untouched.

- Risk: Script tests become brittle by asserting too much generated text.
  Mitigation: Prefer observable Bash completion tests for prefix behavior, with only focused script-string assertions for key candidates.

- Risk: Tests assume every known property belongs to the `init` module.
  Mitigation: Assert each known property on a module that actually declares it in the local runtime catalog.

## Rollout and Recovery

Rollout is normal release of the CLI. Existing users must regenerate or reinstall Bash completion with `seed4j completion bash` or `seed4j completion bash --install`. Recovery is reverting the catalog wiring and docs; apply behavior is unchanged.

## Lessons Learned

- Core Seed4J exposes `defaultValue` but not complete value metadata.
- `NodePackageManager` and `SpringConfigurationFormat` are public enums; end-of-line is not.
- `--plan` is not present in this CLI checkout, so it must not be included in this phase.
- `NodePackageManager.propertyKey()` is the insertable completion value even though the method name sounds like a module property-key accessor.
- `init` declares `--node-package-manager` and `--end-of-line`, but `--spring-configuration-format` is observed on Spring-related modules such as `spring-boot`.
